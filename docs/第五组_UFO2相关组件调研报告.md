# 第五组 UFO2 相关组件调研报告：Coordinator / Security / Knowledge

- 项目名称：Linux 桌面 Agentic OS 设计与实现
- 小组：第 5 组，系统协调 + 安全 + RAG
- 调研主题：UFO2 相关组件理解，聚焦 Coordinator / Security / Knowledge
- 适用范围：课程设计调研报告、第五组设计文档补充、系统集成答辩材料

## 摘要

本报告围绕微软 UFO2（UFO²: The Desktop AgentOS）的系统级组件展开调研，重点分析与第五组职责直接相关的三类能力：Coordinator（系统协调与跨模块编排）、Security（安全隔离、权限控制与审计）、Knowledge（持续知识底座与 RAG 轨迹复用）。UFO2 的核心价值不只是“让智能体会点鼠标”，而是把桌面自动化抽象为一种接近操作系统控制面的能力：HostAgent 负责理解用户目标并拆解任务，AppAgent 负责面向具体应用执行，控制检测模块提供 UIA 与视觉融合的控件定位，Knowledge Substrate 则持续积累应用文档和历史执行经验。对本课程项目而言，第五组处在系统协调层，承担“流程中枢、安全闸门、经验沉淀”的职责，需要把第 1 组到第 4 组的输出组织成可验证、可追溯、可恢复的端到端执行链路。

根据任务书要求，本项目需要在 Linux 桌面环境中实现类似 UFO2 的 Agentic OS 原型，因此不能直接复刻 Windows UIA、Win32、WinCOM 和 RDP PiP 等机制，而应将其思想迁移到 Linux 的 AT-SPI/D-Bus、进程隔离、文件系统权限、审计日志与轻量级知识检索中。第五组当前代码已经实现 `SystemCoordinator`、`SecuritySandbox`、`RAGKnowledgeBase`、`TraceStore` 与 `AuditLogger` 等模块，基本覆盖了 UFO2 中“中央编排、隔离执行、长期记忆”的系统性思想。本报告将从 UFO2 架构入手，分别说明三个组件的功能边界、关键机制、OS 原理映射、Linux 适配方案，以及对本组实现的启示。

## 1. UFO2 架构背景与第五组定位

UFO2 是微软在 UFO 基础上提出的桌面 AgentOS 框架。早期 UFO 主要强调 Windows GUI 场景下的双智能体结构，即 HostAgent 与 AppAgent 协作完成跨应用任务；UFO2 则进一步把桌面自动化提升为系统级抽象，引入更深的操作系统集成、更稳定的 GUI + API 混合动作层、持续知识底座、推测式多动作执行，以及隔离的 Picture-in-Picture（PiP）桌面环境。其目标是解决传统 RPA 和纯视觉 CUA 的共同问题：脚本脆弱、对 UI 变化敏感、缺少应用内部语义、执行时容易抢占用户桌面、缺少长期经验复用。

在 UFO2 中，HostAgent 相当于桌面级调度者，负责接收自然语言请求、拆解任务、选择目标应用、协调多个 AppAgent；AppAgent 面向具体应用，负责识别控件、选择 GUI 或 API 动作、执行并反馈结果；Control Detection 通过 Windows UI Automation 与视觉解析融合，解决标准控件和自绘控件的覆盖问题；Knowledge Substrate 则把应用文档、教程、示例轨迹、执行日志等材料转化为可检索知识，在运行时增强智能体提示上下文。微软官方文档将 UFO2 概括为深度 OS 集成、混合 GUI/API 动作、持续知识学习和并行非侵入式执行等能力。

本课程项目将 UFO2 的 Windows 桌面 AgentOS 思想迁移到 Linux 桌面。第 1 组负责 AI Shell 与 HostAgent，第 2 组负责任务规划和控件检测，第 3 组负责 AppAgent 与 GUI 自动化执行，第 4 组负责工具注册与 OS Skills，第 5 组负责系统协调、安全沙箱与 RAG。因此，第五组不是单纯的“工具调用辅助模块”，而是端到端链路的控制面：在用户意图进入执行系统前进行安全准入，在任务执行过程中统一调度各组模块，在执行后沉淀审计和知识轨迹。

从操作系统原理角度看，第五组对应三个核心主题。第一，虚拟化与资源隔离：安全沙箱通过策略、路径约束、签名验证和隐私保护限制 Agent 对真实系统资源的访问。第二，并发与调度：协调器通过统一流程、超时控制、重试机制和异步写入，把多个模块组织为可控的执行序列。第三，持久性与存储管理：审计日志和 RAG 知识库把一次性执行转化为可追踪、可检索、可复用的长期记录。这正好对应任务书中“虚拟化、并发、持久性”的课程目标。

## 2. Coordinator：系统协调与跨模块编排

### 2.1 UFO2 中的协调思想

UFO2 的协调能力主要体现在 HostAgent 和系统运行时中。HostAgent 不是简单的聊天入口，而是桌面任务的总控者：它需要理解用户请求，判断任务涉及哪些应用，决定何时启动或关闭应用，创建和调度 AppAgent，并维护任务执行状态。论文中描述 HostAgent 运行在 Windows 原生底座之上，能够监控活动应用、发出 shell 命令启动进程、管理应用专属 AppAgent 的创建和销毁，并通过状态机控制执行阶段转换。这里的“Coordinator”思想并不局限于一个类名，而是贯穿在任务分解、生命周期管理、跨应用协调、错误恢复和结果汇聚中。

与传统脚本不同，Agentic OS 的协调器面对的是开放桌面环境：应用可能尚未启动，窗口焦点可能变化，UI 元素可能消失，用户可能同时操作系统，LLM 也可能输出不稳定计划。因此协调器必须具备“阶段化执行”的能力。一般可以抽象为：输入校验、意图解析、安全检查、任务规划、控件定位、动作执行、工具调用、结果验证、日志入库、失败恢复。每一阶段都应有明确输入输出和错误边界，避免某一模块异常扩散到整个系统。

UFO2 的多智能体分层也体现了操作系统调度思想。HostAgent 负责“做什么、何时做、由谁做”，AppAgent 负责“怎么做、在哪里做”。这种分工类似 OS 中调度器与进程/线程执行上下文的关系：调度器不关心每个应用内部细节，但必须维护全局状态、资源使用、失败处理和任务进度。对课程项目而言，第五组的 `SystemCoordinator` 就承担了这个控制面角色，只是输入来自第 1 组的结构化 `intent_json`，执行能力依赖第 2/3/4 组模块。

### 2.2 本项目 Coordinator 的职责边界

第五组的协调器应当坚持“统一入口、清晰契约、弱耦合调用、强可观测性”四个原则。统一入口意味着所有跨组执行都通过 `SystemCoordinator.orchestrate()` 进入，便于集中做安全、审计和异常处理。清晰契约意味着第 1 组输出 `intent_json`，第 2 组输出 `plan_json`，第 3 组输出 `result_json`，第 4 组输出 `tool_result_json`，第 5 组输出统一 `orchestrate_result`。弱耦合调用意味着协调器只依赖接口能力，不绑定其他组内部实现。强可观测性意味着每次调用都必须携带 `trace_id`，并记录阶段、耗时、风险等级、错误码和结果摘要。

当前代码中的 `coordinator/system_coordinator.py` 已经形成了较完整的编排流程：首先为输入补齐或生成 `trace_id`，然后校验必要字段，再调用 `SecuritySandbox.check()` 进行安全检查；安全通过后，按顺序调用第 2 组规划模块、第 3 组执行模块和第 4 组工具模块；最后将执行结果写入审计日志和 RAG 知识库。该流程与任务书中“第 1 组 -> 第 5 组安全检查 -> 第 2 组 -> 第 3 组 -> 第 4 组 -> 第 5 组审计/RAG”的链路基本一致。

协调器中值得保留的设计包括：第一，模块注册机制。通过 `register(group_name, module)` 注册外部模块，能够支持 Mock 与真实模块切换，适合跨组并行开发。第二，超时控制。使用 `ThreadPoolExecutor` 对外部模块调用设置 3 秒超时，防止某个组的模块卡死导致整条链路无响应。第三，失败标准化。通过错误码区分安全拒绝、路径穿越、规划不可用、执行不可用、工具不可用和内部异常，便于联调定位。第四，异步入库。RAG 与审计写入不阻塞主流程，降低演示时延。

### 2.3 Coordinator 的 Linux 适配理解

UFO2 面向 Windows，可直接利用 UIA、Win32、WinCOM 和 RDP loopback；本项目面向 Linux，需要将协调能力建立在更通用的进程、D-Bus、文件系统和 GUI 自动化工具之上。对于第五组而言，Linux 适配重点不是直接操作 AT-SPI，而是为第 2/3 组提供稳定的调用框架和状态管理：第 2 组可通过 AT-SPI/D-Bus 获取控件树，第 3 组可通过 PyAutoGUI 执行动作，第 5 组需要判断何时调用、如何超时、失败后如何返回、如何记录现场。

协调器还应该为演示场景设计可降级路径。任务书要求当其他组落后时第五组提供备用 Mock 实现，因此 `SystemCoordinator` 不应假设所有模块总是存在。当前代码对第 2/3 组未注册会返回标准错误，对第 4 组工具调用则采取可选和降级处理，这种差异是合理的：规划和执行是核心路径，工具调用则可能只在某些任务中出现。后续如果要提升完整性，可以进一步加入 `health_check()` 的演示输出，让答辩时可以直观看到各组模块是否在线。

## 3. Security：安全沙箱、权限控制与审计

### 3.1 为什么桌面 AgentOS 必须内建安全层

桌面智能体和普通聊天机器人最大的区别，是它能够直接影响真实操作系统：移动文件、打开网页、执行命令、读取隐私文件、修改系统设置，甚至可能删除数据或泄露凭据。UFO2 通过 PiP 虚拟桌面、原生 API 检查、状态机和动作验证来降低误操作风险。论文中提到 PiP 将自动化执行放入隔离的虚拟桌面会话，使 Agent 与用户主桌面并行运行，减少对用户输入设备的抢占，也提供了一种 GUI 自动化隔离原语。虽然 PiP 更偏执行环境与用户体验，但它体现了 Security 的核心原则：Agent 的能力越接近 OS 控制面，就越需要隔离、准入、验证和可追溯。

对 Linux Agentic OS 原型而言，安全层至少要解决四类风险。第一是破坏性操作，例如 `rm -rf /`、格式化磁盘、关机、修改系统目录。第二是越权访问，例如读取 `/etc/passwd`、`/root`、`.ssh/id_rsa` 或用户密钥。第三是命令注入和路径穿越，例如把普通路径包装成 `../../etc/passwd`。第四是供应链和接口篡改，例如跨组模块或工具调用参数被伪造。课程项目不要求实现工业级强隔离，但必须展示危险操作被拦截，并能说明安全机制如何与 OS 原理关联。

### 3.2 本项目四层安全架构

任务书要求第五组实现四层安全架构：权限检查、沙箱执行、签名验证、隐私保护。当前 `security/security_sandbox.py` 已经按照这个结构实现，形成了较清晰的层次化防线。

第一层是权限检查。系统通过策略表匹配动作和目标路径，对危险命令、受保护路径、高风险删除等操作进行拦截或风险标记。这相当于操作系统访问控制中的策略决策点，负责判断某个主体是否可以对某个客体执行某类动作。由于 Agent 的主体身份通常来自自然语言意图，策略匹配要同时关注 `action`、`target` 和 `raw_text` 的语义风险。

第二层是沙箱执行检查。当前实现将写类操作限制在 `/home/`、`/tmp/`、`/var/tmp/` 等可控目录中，拒绝向系统关键目录写入。这是课程原型中非常实用的隔离策略：它不依赖复杂容器技术，也能展示“资源隔离”的 OS 思想。若后续在 Linux 环境进一步增强，可以结合 bubblewrap、命名空间、只读绑定挂载等机制，将 GUI 自动化之外的文件操作限制在专用工作目录。

第三层是签名验证。当前实现支持 HMAC-SHA256：当请求参数携带 `signature` 时，必须与 `action|target|params` 生成的签名一致，否则拒绝。这一层可以防止跨组接口传输中参数被篡改，也能为第 4 组工具调用提供来源可信性基础。为了兼容联调，未携带签名时当前默认放行，这符合课程阶段的工程现实；最终答辩时可以说明这是“兼容模式”，真实系统中应对高风险工具强制签名。

第四层是隐私保护。当前实现匹配 `password`、`api_key`、`token`、`secret`、`.ssh`、`id_rsa` 等敏感模式，并对读取、打开、导航等动作进行拦截。这与 AgentOS 的隐私边界密切相关：自然语言代理可能被用户误导，也可能被网页内容或文档内容间接提示攻击，因此对凭据、密钥和隐私目录应默认更保守。

### 3.3 安全结果与审计闭环

安全检查不能只返回“通过/拒绝”，还应该返回风险等级、拒绝原因和命中策略。当前接口 `CheckJSON` 包含 `approved`、`risk_level`、`reason`、`matched_policy`，符合任务书要求。风险等级可用于协调器决策：低风险直接放行，中风险记录审计，高风险要求用户确认，critical 直接拒绝。虽然当前实现主要是自动拒绝或放行，但数据结构已经为后续“人类确认”留出空间。

审计是 Security 的另一半。没有审计，安全策略只能在运行时拦截，无法事后复盘。第五组的 `AuditLogger` 与 `SystemCoordinator._write_audit()` 将安全通过、拦截、规划完成、执行完成、工具调用、失败等事件写入日志，使每个 `trace_id` 都能回放。这一点非常适合答辩展示：可以先输入危险指令，看到系统返回 `E1001` 或 `E1002`，再打开审计日志证明拦截原因和策略编号。

### 3.4 Security 的不足与改进方向

当前安全沙箱已经满足课程验收的核心要求，但仍有若干可说明的局限。第一，策略主要基于字符串和路径规则，对复杂自然语言绕过的理解有限。第二，未真正创建 OS 级隔离环境，文件系统写约束还停留在策略层。第三，高风险但非绝对危险的操作缺少用户确认机制。第四，GUI 动作本身的副作用较难预测，例如点击删除按钮与执行 `rm` 在审计层可能表现不同。改进方向包括：引入操作前预览与确认、将第 3 组 GUI 执行动作也纳入安全检查、使用 bubblewrap 建立真实沙箱目录、对工具调用实施强签名、对隐私路径采用默认拒绝策略。

## 4. Knowledge：知识底座、执行轨迹与 RAG

### 4.1 UFO2 Knowledge Substrate 的作用

UFO2 的 Knowledge Substrate 是其区别于一次性桌面自动化脚本的重要组件。桌面任务通常具有明显的经验性：同一个应用的菜单位置、按钮名称、快捷键、错误弹窗、文件保存路径、常见失败原因都可以被复用。如果每次都完全依赖 LLM 从截图中重新推理，不仅成本高，而且稳定性差。Knowledge Substrate 通过应用文档、在线教程、API 说明、历史执行轨迹和用户反馈，为智能体提供可检索的上下文，使任务规划和动作选择更接近“带经验的操作员”。

在 UFO2 中，知识底座可以服务于多个阶段。对 HostAgent，它能帮助理解用户意图和选择应用；对 AppAgent，它能提供应用专属操作指南、API 用法和控件语义；对安全层，它能沉淀失败案例和风险样本；对系统整体，它能形成可回放的任务轨迹，用于后续调试、评测和持续学习。任务书中要求第五组实现 RAG 知识库，存储执行轨迹并支持检索，正是对 Knowledge Substrate 的课程化落地。

### 4.2 执行轨迹为什么是 AgentOS 的核心资产

执行轨迹不是普通日志。普通日志主要服务于程序员排错，而 AgentOS 的执行轨迹还要服务于未来任务规划。一次完整轨迹至少包括：用户原始输入、结构化意图、安全检查结果、任务计划、控件检测结果、执行动作、工具调用、执行前后状态、错误信息、耗时、风险等级和最终摘要。轨迹越完整，系统越容易回答三个问题：过去类似任务怎么做成的？这次失败发生在哪个阶段？下次遇到同类任务应该避开什么风险？

例如“整理下载目录”是任务书中的复杂验收场景。第一次执行时，系统可能需要经过意图识别、目录扫描、分类规则生成、文件夹创建、文件移动和结果验证。若轨迹被保存，第二次用户提出“把下载目录里的图片和文档分类”时，RAG 可以召回上次成功经验，给规划模块提供更稳定的步骤模板；如果上次因为权限不足失败，RAG 也可以提示协调器或安全层提前检查目标目录权限。这种经验复用正是 Knowledge Substrate 的实际价值。

### 4.3 本项目 RAGKnowledgeBase 设计理解

当前代码中的 `knowledge/rag_kb.py` 采用门面模式封装底层 `TFIDFTraceStore`，对外提供 `add_trace()`、`query()`、`get_trace()`、`stats()` 和 `ping()`。这符合第五组在系统中的位置：知识库不直接参与 UI 操作，而是作为全链路的经验存储与检索服务。协调器在流程完成或失败时调用 `_store_trace_async()` 写入 `TraceRecord`，其中包含 `trace_id`、`action`、`target`、`stage`、`success`、`summary`、`timestamp` 和 `metadata`。这些字段能够支撑最基本的审计追踪与经验查询。

底层 `knowledge/trace_store.py` 实现了轻量级 TF-IDF + 余弦相似度检索，并支持中文字符与英文单词混合分词。由于课程项目规模有限，使用 TF-IDF 而不是完整向量数据库是合理选择：它依赖少、可解释、易测试、启动快，也能体现 RAG 的基本结构。当前实现还支持 numpy 不可用时降级为纯 Python 计算，这对跨平台演示很重要。虽然 TF-IDF 不具备真正的深层语义理解，但对于“打开文件夹”“导航下载”“创建文件夹”“删除被拦截”等短文本轨迹，关键词与字符级检索已经能覆盖大部分验收需求。

`RAGKnowledgeBase.query()` 采用“双通道检索”思想：先由 TF-IDF 召回候选，再通过关键词命中加权重排序。这个设计与 UFO2 的 Knowledge Substrate 思想一致：知识检索不必追求单一算法，而应结合结构化字段和自然语言摘要，让召回结果对执行有用。后续如果接入 LLM 或 Embedding 模型，可以把当前 `TraceRecord` 作为稳定数据模型保留，只替换底层向量化实现。

### 4.4 Knowledge 与审计、安全、协调的关系

知识库不应孤立存在。它与 Coordinator 的关系是“执行后沉淀、执行前辅助”：协调器负责决定何时写入轨迹，也可以在未来版本中在规划前查询相似历史，为第 2 组提供参考案例。它与 Security 的关系是“风险样本库”：所有被拒绝的危险操作也应写入失败轨迹，形成安全测试样本，便于证明系统确实拦截了 `rm`、受保护路径和路径穿越。它与 AuditLogger 的关系是“一个偏检索，一个偏证据”：RAG 面向相似经验召回，审计日志面向完整事件追责。两者都依赖 `trace_id` 串联。

当前实现已经在 `_fail()` 中将失败记录也写入 RAG，这一点很有价值。很多系统只保存成功样本，导致智能体不断重复失败路径；保存失败轨迹后，系统可以在未来任务中学习“哪些动作不应该做”。从 AgentOS 角度看，失败也是知识资产。

## 5. Linux 桌面迁移：从 Windows UIA 到 AT-SPI/D-Bus

任务书要求将 Windows 的 UIA 适配到 Linux 的 AT-SPI/D-Bus。虽然第五组不直接实现控件检测，但理解这一迁移有助于确定协调器和知识库的接口边界。Windows UIA 提供控件树、控件角色、名称、边界框和可执行模式；Linux AT-SPI 也提供类似的辅助功能对象模型，应用通过 D-Bus 暴露可访问对象，客户端可以遍历桌面、应用、窗口和控件，读取角色、名称、状态、位置与动作。

对第 2 组而言，AT-SPI 相当于 Linux 下的结构化 UI 检测通道；视觉检测则是对自绘控件、不可访问控件和图像按钮的补充。对第 5 组而言，关键是要求第 2 组输出稳定的 `plan_json` 和 `elements`，而不是暴露 AT-SPI 内部对象。这样协调器可以保持跨平台：在 Linux 演示时第 2 组使用 AT-SPI，在 Mock 或 Windows 测试时也能返回同样结构。知识库也应记录抽象动作和控件语义，而不是绑定某个 D-Bus 对象地址，否则轨迹复用会受环境变化影响。

此外，Linux 的安全模型与 Windows PiP 不同。Windows UFO2 借助 RDP loopback 和 PiP 隔离桌面交互；Linux 原型可以通过 X11/Wayland 桌面会话、虚拟显示、容器、bubblewrap 或专用用户账号实现不同层级的隔离。课程阶段最可行的是策略沙箱 + 文件路径约束 + 审计日志；若要扩展，可以在演示环境中把 GUI 自动化放入独立用户目录，进一步减少误操作真实桌面的风险。

## 6. 与第五组现有实现的对照分析

从任务书验收点看，第五组需要交付 `SystemCoordinator`、`SecuritySandbox`、`RAGKnowledgeBase` 和审计日志。当前仓库实现与要求基本一致：

1. `SystemCoordinator` 已实现模块注册、健康检查、输入校验、安全检查、规划调用、执行调用、可选工具调用、异步 RAG 入库、审计写入、统计信息和优雅关闭。它对应 UFO2 中的系统控制面，是跨组集成的主入口。
2. `SecuritySandbox` 已实现权限检查、沙箱执行检查、签名验证和隐私保护四层结构，并支持风险等级、策略编号、拒绝原因和风险统计。它对应 UFO2 中的安全执行边界和 OS 资源隔离思想。
3. `RAGKnowledgeBase` 与 `TFIDFTraceStore` 已实现执行轨迹存储、相似查询、按 `trace_id` 精确查找、统计信息、JSON 持久化和 numpy 降级。它对应 UFO2 的 Knowledge Substrate，是历史经验复用与答辩证据追踪的基础。
4. `AuditLogger` 虽然不在本报告主题标题内，但它是 Security 与 Knowledge 的连接层。没有审计，安全策略的效果难以证明；没有轨迹，RAG 无法形成可复用经验。

从工程角度看，现有实现有三个亮点。第一，接口契约集中在 `contracts/schemas.py` 和 `contracts/error_codes.py`，降低了跨组沟通成本。第二，Mock 模块支持独立运行，符合任务书要求的“落后组降级方案”。第三，写入 RAG 和审计均设计为不阻塞主流程，避免知识沉淀拖慢 GUI 演示。

但为了在调研报告和答辩中更完整，也应主动说明改进空间：当前 RAG 仍是轻量级关键词/TF-IDF 检索，不等同于 UFO2 可能使用的更复杂知识底座；当前安全沙箱主要是策略层隔离，不是完整虚拟机或容器沙箱；当前协调器采用顺序编排，尚未实现 UFO2 提到的推测式多动作并行执行；当前知识库主要在执行后写入，尚未在执行前主动检索相似案例辅助规划。这些不足不是缺陷，而是课程原型的合理取舍。

## 7. 对课程验收与报告写作的启示

本组调研报告应突出“理解 UFO2，但不机械照搬 UFO2”。UFO2 的原始环境是 Windows，而课程项目目标是 Linux 桌面 Agentic OS；因此，报告中既要说明 UFO2 的 HostAgent、AppAgent、Control Detection、Knowledge Substrate 等核心组件，也要强调第五组负责的是系统协调层，并解释为什么 Coordinator / Security / Knowledge 是 AgentOS 能否稳定运行的关键。

在验收展示中，第五组可以围绕三个场景组织材料。第一是正常链路：输入“打开文档文件夹”或“整理下载目录”，展示 `trace_id` 如何贯穿安全、规划、执行和入库。第二是安全拦截：输入“删除根目录”“访问 /etc/passwd”“读取 id_rsa”，展示 `SecuritySandbox` 返回拒绝、风险等级和策略编号。第三是知识检索：执行几条任务后查询“打开文件夹”“下载目录”“创建文件夹”，展示 RAG 能召回相关历史轨迹。这三个场景分别对应 Coordinator、Security 和 Knowledge，也能自然覆盖课程评分中的设计、实现、集成和演示项。

## 8. 结论

UFO2 的真正启发在于，它把桌面智能体从单次 GUI 操作提升为系统级运行时：有分层智能体，有结构化控件检测，有混合 GUI/API 动作，有隔离执行环境，也有持续知识底座。第五组负责的 Coordinator / Security / Knowledge 正是 Agentic OS 原型从“能跑”走向“可控、可信、可复用”的关键部分。

Coordinator 解决跨组模块如何被统一调度的问题，使自然语言意图能够稳定流经安全、规划、执行、工具和知识入库阶段；Security 解决 Agent 能力边界问题，使系统能够拦截危险命令、保护系统路径、验证请求签名并阻止敏感信息访问；Knowledge 解决经验沉淀问题，使每次执行都能变成可检索、可审计、可复用的轨迹。三者结合后，第五组不仅完成了任务书中“系统协调 + 安全 + RAG”的功能要求，也体现了操作系统课程强调的虚拟化、并发和持久性思想。

因此，本组后续工作的重点应放在集成稳定性和演示可解释性上：保持接口契约稳定，完善危险操作样例，积累可展示的成功/失败轨迹，并在答辩中用 `trace_id` 串起完整故事。这样既能说明我们理解了 UFO2 架构，也能证明我们将其系统思想落到了 Linux Agentic OS 的可运行原型中。
