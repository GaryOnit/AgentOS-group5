# 第五组 Linux 场景下安全与审计设计思路调研报告

- 项目名称：Linux 桌面 Agentic OS 设计与实现
- 小组：第 5 组，系统协调 + 安全 + RAG
- 调研主题：Linux 场景下安全与审计设计思路，聚焦沙箱隔离 / LSM / AT-SPI 隐私边界 / Agent 审计
- 适用范围：课程设计调研报告、第五组设计文档补充、系统集成答辩材料

## 摘要

本报告围绕将微软 UFO² 架构引入 Linux 桌面环境时的安全与审计设计思路展开调研，重点分析与第五组职责直接相关的四类机制：轻量级无特权沙箱隔离（Bubblewrap）、内核级细粒度资源限制（Landlock LSM）、AT-SPI 与 D-Bus 接口的隐私与边界防御，以及基于工具边界的多维安全审计（Agent Auditing）。

当 Agentic OS 从 Windows 迁移到 Linux 时，不能直接复用 Windows 的 PiP 虚拟桌面、UIA 权限检查和 WinCOM 沙箱机制，而必须结合 Linux 内核特有的安全模型来重构安全防线。Linux 提供了从内核到用户态的完整安全原语栈：命名空间与 seccomp 构成轻量沙箱基础，Landlock LSM 提供无特权进程自我限制能力，AT-SPI/D-Bus 的角色过滤构成 GUI 操作隐私边界，而工具边界审计则是 LLM 生成内容触达真实系统的最后一道关卡。这四层机制与第五组现有四层安全架构（权限检查 / 沙箱执行检查 / 签名验证 / 隐私保护）在设计思想上高度吻合，构成了 Linux Agentic OS 安全体系的完整理论支撑。

## 1. 背景：为什么 Linux 需要重新设计安全防线

UFO² 在 Windows 环境中依赖 PiP 虚拟桌面进行 GUI 隔离，依赖 Win32/UIA 权限模型进行访问控制，依赖 WinCOM 接口进行签名可信验证。这些机制与 Windows 内核和桌面会话管理深度耦合，无法直接在 Linux 上复用。

Linux 桌面 Agentic OS 面临同等乃至更复杂的安全挑战。智能体能够通过 AT-SPI 遍历控件树、通过 D-Bus 发送消息、通过文件系统接口读写数据，其能力触达范围覆盖从 GUI 层到内核接口层的完整栈。LLM 生成动作存在不确定性，既可能因幻觉产生危险指令，也可能被提示注入攻击诱导执行越权操作。任务书对第五组的安全要求——权限检查、沙箱执行、签名验证、隐私保护——正是对这些风险的系统化应对。

Linux 内核和桌面生态为此提供了一套完整的原语：Bubblewrap 提供无特权命名空间沙箱，Landlock 提供进程自我限制的 LSM 机制，AT-SPI 提供控件角色过滤接口，D-Bus 提供消息超时与策略控制，而工具边界审计则将所有安全事件转化为可追溯的证据链。本报告逐一分析这四类机制，并说明其与第五组现有实现的对应关系。

## 2. 轻量级无特权沙箱隔离（Bubblewrap）

### 2.1 基本原理

Bubblewrap（bwrap）是一个轻量级命令行沙箱工具，被 Flatpak 等主流 Linux 应用分发框架广泛采用。它利用 Linux 内核的用户命名空间（user namespace）、挂载命名空间（mount namespace）、PID 命名空间等机制，在不需要 root 权限的情况下为进程创建隔离的执行环境。

其核心安全设计体现在两点。第一，命名空间隔离：沙箱内的进程拥有独立的文件系统视图、PID 空间和网络接口，与宿主系统形成逻辑隔断；挂载点可以被配置为只读绑定，防止沙箱内进程对真实文件系统产生持久副作用。第二，seccomp 过滤：Bubblewrap 在沙箱内启用 seccomp BPF 过滤规则，精确限制允许调用的系统调用集合，对 `execve`、`socket`、`ptrace` 等高风险系统调用进行拦截，显著缩小攻击面。

### 2.2 与 Agentic OS 的结合

在 Linux Agentic OS 中，系统调用 OS Skills 或执行底层文件操作时，必须避免在真实主机环境中直接运行。Bubblewrap 能够为这类操作提供轻量级的底层沙箱支持，具体体现在以下三个方面。

第一，特权剥夺：Bubblewrap 剥夺了沙箱内的 `CAP_SYS_ADMIN`、`CAP_NET_ADMIN` 等能力集，且强制规定子进程无法获得比父进程更高的操作权限（即 `no_new_privs` 标志），从源头阻断了恶意指令的提权路径。这一特性对 Agentic OS 尤为重要：LLM 生成的动作无论意图如何，都无法在沙箱内通过提权突破宿主系统边界。

第二，文件系统隔离：通过只读绑定挂载，沙箱可以只暴露智能体执行任务所必需的目录，例如用户下载目录或临时工作目录，而将系统目录（`/etc`、`/usr`、`/root`、`/boot`）完全排除在沙箱视图之外。

第三，副作用可控：沙箱内的文件操作不会超出预定工作目录，即使 LLM 输出了危险的删除或覆写指令，其实际影响范围也被限制在可恢复的隔离空间中。

### 2.3 与第五组实现的对应关系

第五组现有实现中的第二层安全检查（沙箱执行检查）通过策略表将写类操作限制在 `/home/`、`/tmp/`、`/var/tmp/` 等可控目录，拒绝向系统关键目录写入。这一设计在课程原型阶段是合理的策略层隔离。Bubblewrap 代表了在此基础上进一步增强的工程方向：从策略检查升级为 OS 级隔离执行，使隔离不再依赖代码路径的完整覆盖，而是由内核强制执行。若后续在 Linux 演示环境中集成 Bubblewrap，可以将第 4 组的 OS Skills 执行封装在沙箱进程中，同时保持第五组协调器对外接口不变。

## 3. 内核级细粒度资源限制（Landlock LSM）

### 3.1 基本原理

Landlock 是 Linux 内核 5.13 版本引入的可堆叠安全模块（LSM），其设计目标是赋予无特权进程安全地限制自身访问权限的能力。与传统 LSM（如 SELinux、AppArmor）需要系统管理员预先配置全局策略不同，Landlock 允许进程在运行时主动声明自己的最小权限集合，从而实现"按需赋权"的最小化授权原则。

Landlock 的访问控制基于文件系统路径和网络接口的精确拦截。进程可以声明"我只需要读取 `/home/user/Documents`，其他路径一律不可访问"，或"我不需要任何网络连接"。一旦策略被提交（通过 `prctl(PR_SET_SECCOMP)` 类似接口），进程无法反悔——策略只能进一步收紧，不能放宽。子进程继承父进程的 Landlock 约束，并可在此基础上叠加更严格限制。

### 3.2 防范 LLM 不可靠动作的应用价值

大语言模型生成的动作存在语义正确但执行边界模糊的问题。例如，用户说"整理桌面文件"，LLM 可能生成覆盖 `/home/user/.bashrc` 或删除 `/home/user/.config` 的操作计划，这些操作在语义上与"整理"相关，但在执行上可能造成不可恢复的后果。

将 Landlock 与 Agent 执行器结合，可以构建"按需赋权"的安全层。在任务开始前，协调器根据任务类型声明执行器仅需访问的目录集合（例如 `/home/user/Desktop/`），提交 Landlock 策略后启动执行进程。即使 LLM 生成了越界操作，执行进程在内核层面也无法完成该操作，错误会以标准系统调用失败返回，而非静默完成危险动作。这一机制可将意外或恶意行为对用户态造成的影响降低到最小化边界内。

### 3.3 与第五组实现的对应关系

Landlock 的思想与第五组第二层安全检查（沙箱执行检查）和第一层权限检查（策略命中）的设计目标高度一致。区别在于，Landlock 是内核强制执行，而当前实现是用户态代码路径检查。两者并不互斥：用户态检查速度快、可提供精确错误码和拦截日志，内核层 Landlock 则作为最终兜底防线。在答辩中引用 Landlock，可以说明第五组的安全设计具备向更强隔离升级的工程路径，并非课程原型的一次性实现。

## 4. AT-SPI 与 D-Bus 接口的隐私与边界防御

### 4.1 AT-SPI 的隐私风险

AT-SPI（Assistive Technology Service Provider Interface）是 Linux 桌面的无障碍功能接口，允许客户端程序遍历桌面上所有应用的控件树，读取控件角色、名称、状态、位置和可执行动作。UFO² 的任务规划层依赖类似机制遍历 Windows UIA 控件树；本项目的第 2 组通过 AT-SPI 实现 Linux 控件检测。

AT-SPI 在设计上面向无障碍辅助需求，不假设调用者存在恶意。这意味着，在未加限制的情况下，任何应用（包括 LLM 驱动的 Agent）都可以通过 AT-SPI 读取密码管理器的输入框内容、终端输出文本、私信应用的消息列表，甚至触发密码字段的值变更。对 Agentic OS 而言，这是一个需要主动防御的隐私边界。

### 4.2 敏感角色屏蔽

AT-SPI 为每个控件定义了角色（role）属性，例如 `ROLE_PASSWORD_TEXT`、`ROLE_ENTRY`、`ROLE_TERMINAL`。自动化操作引擎在访问控件时，必须强制屏蔽 `PASSWORD_TEXT` 等敏感角色属性，防止智能体读取密码管理器、终端输出或高隐私数据来源中的明文内容。

具体实现上，第 2 组的控件检测模块应在控件信息返回给协调器之前，对角色为敏感类型的控件进行脱敏或跳过处理。第五组的隐私保护层（第四层安全检查）则在意图层面对包含 `password`、`api_key`、`token`、`.ssh`、`id_rsa` 等敏感模式的目标进行拦截，形成"意图层 + 控件层"的双重隐私防线。

### 4.3 D-Bus 接口的超时强制执行

D-Bus 是 Linux 桌面的进程间通信总线，AT-SPI、应用菜单、系统服务等大量桌面功能通过 D-Bus 暴露接口。Agent 在通过第 3 组执行 GUI 动作时，底层往往依赖 D-Bus 调用。

如果对 D-Bus 调用不设置超时限制，死循环操作或无响应应用可能导致整个 Agent 执行链路挂起，进而引发系统级卡死。因此，必须对所有的 D-Bus 调用强制执行超时限制（Timeouts）。这与第五组协调器中对第 2/3/4 组模块调用设置 3 秒超时的设计理念一致：超时不是性能优化，而是安全稳定性的基本保障，防止单个不可控外部模块导致全系统不可用。

### 4.4 与第五组实现的对应关系

第五组的隐私保护层（第四层安全检查）已在意图层面覆盖敏感模式拦截，协调器已实现模块调用超时控制。AT-SPI 角色过滤属于 Linux 特有的额外防线，可作为第五组安全架构在答辩中展示的"Linux 适配增强点"：说明在真实 Linux 部署中，第 2 组返回控件信息前应进行角色过滤，第五组协调器在接收到控件信息后也会进行二次隐私检查，形成多层防御。

## 5. 基于工具边界的多维安全审计（Agent Auditing）

### 5.1 工具边界的核心地位

工具函数是 LLM 生成内容触及真实系统的执行边界。无论 LLM 的推理多么复杂，最终影响系统状态的动作都必须通过工具调用（文件操作、进程控制、D-Bus 消息、GUI 动作触发）完成。这使工具边界成为安全审计的最关键节点：在工具执行前后进行数据流分析和权限风险排查，能够以最小的检查面覆盖最大的安全风险。

审计系统必须在这些关键节点进行数据流分析和权限风险排查。具体而言，审计记录应至少包含：工具名称、调用参数、调用来源（`trace_id`）、执行前系统状态快照、执行结果、执行后状态变化、风险等级和时间戳。这些字段使审计日志不仅能回答"发生了什么"，还能回答"为什么发生"和"造成了什么影响"。

### 5.2 语义检查与沙箱观测的分离记录

先进的 LLM 智能体审计要求将语义层面的检查与在沙箱中观测到的实际状态变更（Sandbox-observed harm）分离记录。这一要求来源于当前 LLM 安全研究的一个核心洞察：LLM 的意图描述（语义）和实际执行效果（物理）可能存在偏差，单纯依赖语义过滤（即分析 LLM 输出的文本）不足以判断真实危害。

分离记录的具体含义是：

- **语义审计记录**：记录 LLM 输出的动作描述、安全策略命中结果、风险等级评分。这对应第五组第一层（权限检查）和第四层（隐私保护）的拦截结果。
- **沙箱观测记录**：记录工具实际执行后的文件系统变更、进程状态变化、网络连接行为等可观测的物理状态。这对应执行层的实际副作用，与 LLM 描述的意图无关。

两类记录通过 `trace_id` 关联，使安全分析人员在事后复盘时能够对比"LLM 说要做什么"与"系统实际发生了什么"，精确定位语义与执行之间的偏差来源。

### 5.3 审计日志与 RAG 知识库的闭环

每次操作执行后，相关带有时间戳的审计日志会由系统协调器捕获，并作为执行轨迹固化存储到 RAG 知识库中，为事后安全溯源提供完整依据。这一设计使审计不只是面向当次事件的记录，而是面向未来任务的知识资产：

- 成功轨迹可以为后续类似任务提供操作模板，降低对 LLM 重新推理的依赖。
- 失败轨迹和拦截记录可以形成"反例知识库"，在未来任务规划前主动查询，避免重复触发已知危险路径。
- 安全拦截事件的审计记录可以作为系统安全能力的可验证证据，支撑验收答辩中"危险操作被拦截"的现场演示。

第五组现有实现中，`AuditLogger` 记录全链路审计事件，`RAGKnowledgeBase` 存储执行轨迹，`SystemCoordinator._fail()` 在失败时同时写入审计和 RAG 失败记录。这一设计已经体现了审计与知识库闭环的核心思想，在答辩中可以通过 `trace_id` 串联展示"一次操作从执行到审计到可检索"的完整链路。

### 5.4 审计记录的完整性要求

为了使审计记录具备事后安全溯源能力，每条记录应满足以下完整性要求：不可篡改性（日志采用追加写入，禁止修改历史记录）、时间可信性（时间戳应尽可能来自系统单调时钟）、关联可达性（所有记录必须携带 `trace_id`，支持从任意事件反查完整执行上下文）、敏感信息脱敏（审计记录中不应包含明文密码、API 密钥等隐私数据，参数中的敏感字段应在写入前脱敏处理）。

当前 `AuditLogger` 采用 JSONL 格式追加写入，字段涵盖 `trace_id`、`event`、`detail`、`timestamp`，基本满足追加写入和关联可达的要求。进一步增强方向包括在写入 `security_result` 时对敏感字段进行掩码处理，以及为高风险拦截事件单独维护不可删除的审计专用存储。

## 6. 四类机制与第五组实现的整体对照

从上述四类 Linux 安全机制来看，第五组现有四层安全架构与这些 Linux 原生机制在设计思想上形成了完整的对应关系：

| Linux 安全机制 | 对应第五组安全层 | 当前实现状态 |
|---|---|---|
| Bubblewrap 命名空间沙箱 / seccomp | 第二层：沙箱执行检查（写目录约束） | 策略层实现，Bubblewrap 集成为增强方向 |
| Landlock LSM 最小权限 | 第一层：权限检查（策略命中） + 第二层：路径约束 | 策略层实现，Landlock 集成为增强方向 |
| AT-SPI 角色过滤 / D-Bus 超时 | 第四层：隐私保护（敏感模式拦截） + 协调器超时 | 意图层拦截 + 调用超时已实现 |
| Agent 工具边界审计 | 审计日志 + RAG 执行轨迹 | AuditLogger + RAGKnowledgeBase 已实现 |

这一对应关系说明，第五组的安全设计不是孤立的规则集合，而是具有 Linux 系统安全理论支撑的分层防御体系。课程原型阶段在用户态实现策略层，为后续在 Linux 内核机制层面的增强预留了清晰的升级路径。

## 8. 结论

在将 UFO² 架构引入 Linux 桌面环境时，安全防线的重构必须深度结合 Linux 内核特有的安全机制与无障碍接口特性。Bubblewrap 提供了无特权命名空间沙箱，从执行层阻断提权路径；Landlock LSM 赋予进程自我限制能力，实现"按需赋权"的最小化授权；AT-SPI 角色过滤与 D-Bus 超时控制构建了 GUI 操作的隐私与稳定边界；基于工具边界的多维审计将语义检查与沙箱观测分离记录，形成可追溯的完整安全证据链。

这四类机制与第五组现有四层安全架构（权限检查 / 沙箱执行检查 / 签名验证 / 隐私保护）在设计目标上高度一致，在工程实现上构成了"课程原型用户态实现 + 内核机制增强方向"的完整安全设计体系。第五组的安全与审计设计不仅满足任务书的课程验收要求，也体现了 Linux Agentic OS 在真实部署场景中的系统安全思想：从意图识别到工具执行，每一个边界都应有拦截；每一次执行，无论成功还是失败，都应形成可审计、可检索的持久化证据。
